Many of them had `.widthIn(max = ...).fillMaxWidth(...)` combinations to force layout widths, which should ideally be handled via row weights or not hardcoded at the use site if the layout is truly flexible.

## 2024-09-02 - UI Refactor
**Learning:** Found several inconsistent and hard-to-maintain hardcoded modifiers on `HordeButton` and `HordeSecondaryButton` uses across screens like `MainMenuScreen`, `PauseScreen`, and `GameOverScreen`. Given the specific instruction in memory: "avoid hardcoding layout constraints like `.fillMaxWidth()` inside the base component; instead, allow callers to pass them via the modifier parameter", I will simply leave them to be passed in. However, to ensure consistency and clean up the call sites, I can extract common layouts into styled buttons or clean up the calls.
## 2024-09-01 - Consolidate UI Interaction Logic
**Learning:** Found multiple duplicate implementations of button interaction logic (`MutableInteractionSource`, `isPressed`, `isHovered`, scale animations, and sound triggers) across `HordeUI.kt` (`HordeButton`, `HordeSecondaryButton`, `HordeItemCard`, etc.). Leaving interactive visual states duplicated creates inconsistencies and makes it difficult to adjust the game's overall "feel" (like bounce stiffness or sound behavior).
**Action:** Extracted the entire interaction pattern into a reusable Compose `Modifier.hordeInteractive()`. Replaced the repetitive code in `HordeUI.kt` with this shared modifier. Whenever possible, visual interaction states (hover, press, disable) should be encapsulated in a modifier rather than rebuilt in every button variant.
